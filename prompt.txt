# Senior .NET + Vue Architect — Welco & Snul System Analysis & Implementation

You are acting as a **Senior Software Architect, Senior .NET Backend Engineer, Senior Vue.js Engineer, and Database Architect**.

I already have two fully implemented systems:

* **Welco** → Pakistan website/system
* **Snul** → Egypt website/system

Both systems are already implemented using a **Microservices architecture** with:

* Vue.js frontend
* .NET backend
* API Gateway
* Multiple backend microservices
* Separate databases
* Authentication/Authorization
* Existing business logic

Your job is NOT to rebuild the systems from scratch.

Your job is to:

1. Analyze the existing codebase deeply.
2. Understand the current architecture and business logic.
3. Identify architectural and business-logic gaps.
4. Modify and improve the existing implementation.
5. Preserve the existing architecture wherever possible.
6. Implement the required Welco ↔ Snul integration correctly.
7. Keep both systems independently deployable and maintainable.

---

# 1. CRITICAL BUSINESS ARCHITECTURE

The two systems MUST remain separate.

```text
Welco
Pakistan Frontend
        ↓
Pakistan API Gateway
        ↓
Pakistan Microservices
        ↓
Pakistan Databases
```

```text
Snul
Egypt Frontend
        ↓
Egypt API Gateway
        ↓
Egypt Microservices
        ↓
Egypt Databases
```

DO NOT merge the databases.

DO NOT create a shared database.

DO NOT make Snul directly access Welco databases.

DO NOT make Welco directly access Snul databases.

Communication between the two systems must happen through secure backend-to-backend APIs.

# 3. IMPORTANT PROVIDER BUSINESS RULE

Providers belong to Welco/Pakistan.

However, a Provider can operate in:

* Pakistan only
* Egypt only
* Both Pakistan and Egypt

Do NOT duplicate the Provider between systems as two unrelated Providers.

A Provider should have a market availability concept.

Example:

```text
Provider: ABC Medical

Pakistan: Active
Egypt: Active
```

Another:

```text
Provider: XYZ Pharma

Pakistan: Active
Egypt: Inactive
```

Another:

```text
Provider: DEF Company

Pakistan: Active
Egypt: Inactive
```

Implement this using a proper domain model such as:

```text
Provider
ProviderMarket
Market
```

or improve the existing implementation if an equivalent concept already exists.

The Provider itself remains a Welco master entity.

---

# 4. PROVIDER APPROVAL

Provider registration should be separated from Provider market availability.

Use a lifecycle such as:

```text
Pending
Approved
Rejected
Suspended
```

Do NOT mix:

```text
Provider Role
```

with:

```text
Provider Approval Status
```

A user can have:

```text
Role = Provider
ProviderStatus = Pending
```

and later:

```text
Role = Provider
ProviderStatus = Approved
```

Only approved providers should be allowed to participate in the relevant business operations.

Products are mastered by Welco.

The main Product entity should remain in Welco.

Snul may maintain a synchronized/local representation of the product for performance and independent operation.

Use a clear external relationship such as:




The systems must never accidentally treat these as unrelated products.

# 8. WAREHOUSE AND INVENTORY

There is currently **ONE physical warehouse**.

The warehouse belongs to Welco/Pakistan.

There is NO Egypt warehouse.

There should NOT be an independent Egypt inventory source of truth.

The inventory source of truth is:

```text
Welco
    ↓
Pakistan Warehouse
    ↓
Inventory Service
```

Snul may cache/display availability, but the final stock validation must happen through Welco.

Example:

```text
Snul Customer
    ↓
Snul Order
    ↓
Welco Inventory Service
    ↓
Check/Reserve Stock
    ↓
Success
```

Prevent race conditions and overselling.

If the existing Inventory Service supports reservation, use it.

If not, implement a safe reservation/transaction mechanism.

Do not simply subtract inventory independently from Snul.

# 10. IDEMPOTENCY

This is critical.

If Snul sends the same order request twice because of:

* network timeout
* retry
* gateway failure
* client retry
* service restart

Welco MUST NOT create two orders.

Implement idempotency using a stable external order/reference ID.

Example:

```text
SnulOrderId = EG-1001
```

If Welco already processed:

```text
EG-1001
```

return the existing Welco Order instead of creating another order.
